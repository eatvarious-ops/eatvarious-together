# 개발 범위와 품질 규칙

AI가 작업을 시작할 때 적용하는 규칙이다. 팀원은 README의 한 문장으로 요청하고, AI가 목표·영역·변경할 기능과 파일·완료 기준·검증 방법을 정리한다. 확정된 내용은 알린 뒤 진행하고, 결과를 바꾸는 미정 사항만 질문한다.

문서 작업은 문서 영역으로 분류하며, 코드나 화면을 만들지 않고 내용·링크·규칙 간 일관성을 검증한다. 환경 구성은 별도 작업으로 등록하고 각 영역의 실행 기반과 공통 설정 범위를 명시한다. 앱 기반이 없는 상태에서 기능 요청을 받으면 필요한 환경 구성 작업과 연결 순서를 정하고, 승인되지 않은 앱 전체를 임의로 만들지 않는다.

## 영역별 작업 경계

| 영역 | 구현 범위 | 확인할 결과 |
| --- | --- | --- |
| 백엔드 | 저장·조회, 업무 규칙, API, 접근 권한 | 입력·응답, 데이터 변경, 잘못된 입력, 권한 없는 요청, 영향받는 기존 동작 |
| 프론트엔드 | 요청한 화면, 사용자 입력, 화면 상태, 확정된 API 연결 | 사용자 조작, 로딩·빈 결과·오류 표시, 기존 화면, 필요한 화면 크기 |

- 백엔드 작업에 확인용 UI나 화면을 임의로 만들지 않는다. API와 데이터 동작으로 검증한다.
- 프론트엔드 작업에서 데이터 구조·API·판정 규칙을 임의로 바꾸지 않는다. 화면 제작·디자인 변경도 요청 범위에 포함될 때 수행한다.
- “기능 구현”만으로 두 영역 전체가 승인됐다고 판단하지 않는다. 요청과 기능정의서로 영역이 식별되지 않으면 필요한 선택만 묻는다.
- 두 영역을 변경해야 하면 각각의 작업과 PR로 분리하고 연결 순서를 정한다. 공통 계약 변경은 담당 작업과 영향을 명시한다.

## API와 데이터 약속

기존 API와 데이터 약속을 먼저 찾아 재사용하고, 필요한 입력·응답·오류·데이터 상태 중 빠진 부분만 구현 전에 문서로 정한다. 실제 앱 구조가 생기면 공통 계약 문서의 위치를 README에 연결한다. 상대 영역이 준비되지 않으면 확정한 약속을 기준으로 검증하고 실제 연결은 미확인으로 기록한다. 모의 응답이나 임시 데이터 사용을 실제 연결로 보고하지 않는다. 약속을 바꿀 때에는 상대 작업에 미치는 영향을 확인한다.

## 요청 밖 구현 방지

요청한 동작과 완료 기준을 충족하는 최소 변경만 수행한다. 관련 없는 개선, 새 라이브러리, 디자인 변경, 향후 기능, 대규모 구조 변경은 임의로 추가하지 않는다. 별도 개선이 필요하면 이유와 영향을 적어 새 작업으로 제안한다. 우연히 발견한 문제도 이번 작업을 막는지 판단하고, 무관하면 별도 기록한다.

요청한 동작에 직접 필요한 내부 수정과 검사는 해당 영역의 범위에 포함한다. 구현에 필요한 의존성이 없으면 기존 도구로 가능한지 확인하고, 새 의존성이 꼭 필요할 때 이유와 범위를 알린다. 다른 영역이나 제품 정책을 바꿔야 하면 해당 변경 전 범위를 확인한다.

## 검증과 셀프리뷰

1. 해당 영역의 검사로 완료 기준과 대표적인 빈 값·경계값·오류 상황을 확인한다.
2. 영향을 받는 기존 동작을 확인한다. 백엔드는 API·데이터·권한을, 프론트엔드는 실제 화면과 조작을 확인한다.
3. 변경 차이를 검토해 요청 밖 기능, 상대 영역의 수정, 비밀값, 불필요한 파일이 섞이지 않았는지 확인한다.
4. 실행한 검사와 실제 결과, 미실행 이유, 상대 영역과 실제 연결 여부를 PR에 남긴다. 각 영역의 검사 통과를 전체 연결 완료로 표시하지 않는다.

실패를 숨기기 위해 검사를 삭제·생략하거나 기준을 낮추지 않는다. 요구사항 변경으로 검사 수정이 필요하면 변경 이유와 대체 검증을 함께 검토받는다.

실제 프로젝트 설정과 잠금 파일에서 설치·실행·검사 방법을 확인한다. 문서에 명령이 없으면 찾아 실행하고 확인된 방법을 README에 보완한다. 검사는 해당 변경의 위험과 완료 기준에 맞춰 수행하며, 의미 없는 검사나 무관한 전체 재검사를 늘리지 않는다. 필수 검사 실패·미실행과 미확인 연결은 PR에 명시한다. 연결 검증이 별도 작업이면 현재 영역의 완료 기준으로 판정하되 전체 연결 완료로 보고하지 않는다. 현재 작업의 필수 연결 검증이 빠졌다면 완료로 처리하지 않는다.

## 실패와 인계

최초 실패를 확인한 뒤 같은 문제에 대한 수정·재검증을 기본 2회까지 수행한다. 해결되지 않으면 해당 문제의 반복 시도를 멈추고 실패 조건, 시도한 수정, 실제 결과, 남은 원인과 필요한 결정을 보고한다. 이 문제 때문에 완료할 수 없으면 검토용 초안 PR 또는 인계 자료를 남긴다. 독립적인 작업은 계속할 수 있다. 실패한 필수 검사는 완료로 판정하지 않는다.

실제 실수의 원인과 다음 행동은 [실수 기록](mistakes.md)에 남긴다. 반복되면 자동 검사로 만들고, 영향이 큰 행동은 권한 설정으로 제한한다. 가상의 사고를 실제 발생 기록으로 작성하지 않는다.

## 실행 장치 구성과 현재 상태

작업 3의 PR 검사 정의와 영역별 로컬 명령은 README에서 확인한다. CODEOWNERS는 리뷰 대상을 지정한다. 폴더 쓰기 제한과 필수 검사에 따른 병합 차단은 별도 저장소 설정이 필요하다. 보호 규칙이나 개발·운영 프로젝트 분리의 실제 적용은 확인한 결과만 기록한다.

앱 환경 구성 작업의 완료 기준에는 다음 항목을 포함한다.

- 백엔드·프론트엔드의 실제 폴더와 공통 계약 위치를 구분하고 README에 안내한다.
- 영역별 실행·검사 명령을 직접 실행해 확인하고 README에 기록한다.
- PR에서 영역별 필수 검사를 자동 실행하고, 실패 시 병합이 차단되는지 저장소 설정을 확인한다.
- 개발·운영 데이터와 자격증명을 분리하고 개발에 필요한 권한만 제공한다.
- 작업 파일과 검사 파일의 보호 경계를 도구 설정으로 구성하고 실제로 적용되는지 확인한다. 쓰기 제한이 읽기까지 차단하는 것은 아님을 구분한다.

각 장치는 설정 위치와 검증 결과를 기록한 뒤에만 적용 완료로 표시한다.
